The problem

A public ledger publishes every recipient's amount, forever.

For a grant programme, a bounty platform, or an aid disbursement, that is disqualifying. It exposes how much each person received to anyone who looks — including people with an interest in knowing which individuals just received money. The usual answer is to pay off-chain, which gives up the auditability that made paying on-chain worth doing.

Tally keeps both halves: amounts stay private, and the round's total stays provable.

What the proof does and does not assure

The donor is assured that the confidential transfers sent from the lane accounts Tally declared on-chain before the round opened, within that round's declared ledger window, total exactly the disclosed amount and that none has been withheld — because every confidential transfer publishes its sender address on-chain whether or not the funder chooses to disclose it, so an omitted transfer is visible as one the proof fails to cover.

This does not assure that the funder made no other payments, nor that the recipients are independent of the funder: the guarantee is scoped to transfers from the accounts declared before the round, not to the funder's total spend, and it establishes what amounts moved, not who ultimately controls the accounts that received them.

Those two sentences are the whole claim. Nothing elsewhere on this page states it more strongly.

Two proving modes, deliberately different

Transfer proofs go on chain, where Nethermind’s verifier implements only the non-zero-knowledge flavour — so they are 14,592 B and non-zk, as the upstream specification requires. The disclosure proof is different. It is verified off chain by the donor, so that limitation does not apply, and it runs in zero-knowledge mode at 16,224 B.

That distinction is load-bearing rather than pedantic. A non-zk proof is succinct but not witness-hiding, so under the on-chain mode the individual amounts would be protected only by the commitments on chain — not by the artifact handed to the donor. The donor already learns the total; only zero-knowledge mode establishes that they learn nothing else. It costs +1,632 B and about 50 ms.

Batching is not possible today. Instructions bind, not bytes — a fact that is invisible until measured, and one we got wrong ourselves before measuring: our first estimate assumed transaction size was the limit and put 7–8 transfers in a transaction. So one-to-many is a fan-out across lanes rather than a loop inside one call. SLP-0004 raises exactly the cap that binds, 4×, which would take this from 1 to 4 with no change on our side.

Verify a published round yourself

Every verification we had done before this existed was performed by whoever generated the proof, which is evidence of nothing. So a real testnet round is published — funder address, round id, and the disclosure bundle — and anyone can check it with no help from us:

two minutes, from a clean clone
git clone --recurse-submodules https://github.com/Tally-Network/Tally
cd Tally && pnpm install
pnpm verify:evidence

→ TOTAL DISBURSED: 3160  over 16 transfers from 5 declared lanes
  no individual amount was revealed.

The verifier takes exactly three values from the funder — the proof, r_disc, and the sealed total. The lane set, the window, the transfer set and every account key are resolved from the chain, so a funder cannot choose which transfers the total covers.

It expires, and that is a real limit. Soroban RPC serves about seven days of events, and verification deliberately reads transfers from the chain rather than from anything we hand over — so this round stops being checkable around ledger 4410007. The tool detects that and says so, rather than reporting an empty result that would look like a failed proof. One command republishes a fresh round. What none of that fixes is verifying a round from last year, which is exactly the case a grant auditor has: that needs the persistent event archive the Stellar specification defines and we have not built it.

The demo is built to be able to fail

Every run sends one transfer before the round opens. It must be excluded, and the donor's total must come out 3,160 rather than 4,159. A demo in which everything falls inside the window cannot distinguish a working completeness check from one that returns every event regardless — so the failing case is permanent, not a one-off.

How it works

The donor holds no secret of the funder's.

A donor generates its own disclosure keypair and issues a fresh challenge nonce. The funder returns a zero-knowledge proof sealed to that key which reveals only the total. The funder's viewing key is never shared — it would open every individual amount, retroactively.

Confidential tokenamounts encrypted
Recipientsaddresses public
Donor / auditorchallenge → proof → total

Completeness comes from the chain

Every confidential transfer publishes its sender and recipient as indexed event topics, unconditionally. A donor enumerates the round's transfers from chain state rather than from anything the funder hands over, so a withheld transfer surfaces as a set mismatch, not a smaller total.

The window is fixed before the round runs

The registry stamps the opening ledger itself — it is not a parameter a caller can supply — and the lane set cannot be revised afterwards. Without that, a funder could run the round first and declare only the flattering accounts.

The donor reads the anonymity set, rather than trusting us for it

A total over one payment is that payment. So the number of transfers an aggregate covers, n_active, is a public input to the proof — the donor reads the true set size and can apply a stricter floor of its own. And the minimum is a circuit constraint, not a library check: an undersized aggregate is unprovable, not merely discouraged. Bypassing our SDK cannot produce a one-payment “aggregate”.

Built on Stellar

Native to the confidential-token primitive, not ported onto it.

Tally is built on Stellar's Confidential Tokens developer preview — the OpenZeppelin contract suite with Nethermind's UltraHonk verifier — which gives any SEP-41 token private balances and private transfer amounts while keeping addresses visible.

Status

Testnet. Here is exactly what is built and what is not.

The confidential-token suite Tally builds on is an unaudited developer preview on an unmerged branch. Nothing here should touch real value yet, and we would rather say so than let a reviewer discover it.

Real people, real wallets, real keys, real verification — nominal value. The round runs on Stellar testnet, where the asset has no monetary worth; what is real is that independent contributors hold their own keys, that no platform can decrypt their amounts, and that anyone can verify the total.
